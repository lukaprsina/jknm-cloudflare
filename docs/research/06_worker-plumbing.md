## 1. Queue + cron composition (measured)

Code: `lib/spike/worker-entry.ts` (`export *` from `vinext/server/fetch-handler`, `default = { fetch, scheduled, queue }`, each wrapped in `runWithDb(drizzle(new Pool(Hyperdrive)))`), `cloudflare.config.ts` (`bindings.queue`, `triggers.queue`, `triggers.scheduled`, types in `workers-sdk/packages/config/src/{bindings,triggers}.ts`). Probe routes under `app/spike/plumb/*`.

- `cf deploy --prebuilt --mode production` created the queue producer binding, the queue consumer and the cron trigger from the typed config (`Producer for ...`, `Consumer for ...`, `schedule: * * * * *`). The Queue itself must exist first (`cf queues create --queue-name ...`); R2 bucket for the Response Store is auto-provisioned.
- Queue: message sent from a Route Handler (`env.QUEUE.send`) was consumed in about 15 s (batch timeout was 1 s; the rest is queue pickup), `attempts: 1`, the consumer's `select count(*) from articles` through the `db` proxy returned 908.
- Cron: the deployed trigger first fired about 5 min after deploy (23:05:40 UTC for a 23:00 deploy), then every minute. Plan for propagation delay after deploying a new trigger. Cron body also ran the db proxy.
- **Direct `revalidateTag` (imported from `next/cache` inside the entry's `queue`/`scheduled`)**: returns without error, log says success, cached read stayed stale (cached counter 1 while truth 2; again after the cron run). No-op for both handlers, confirming the local result in 03.
- **Via `handler.fetch(new Request("http://localhost/spike/cache/outside?fn=revalidateTag&tag=plumb"), env, ctx)`**: route returned 200, the next cached read showed the new counter (queue: 0 to 1; cron: 1 to 2). Works for both. This also confirms the Response Store invalidation works deployed and not only locally.
- Consequence for the handoff (unchanged from 03, now deployed-verified): `apply_internal_invalidations` must go through the vinext handler. Note the internal route is also reachable from the internet through `fetch`; guard it in the entry (reject `/__internal/*` unless the call comes from the in-process `handler.fetch` path, e.g. a secret header set only there) rather than the old `REVALIDATE_SECRET` env scheme.
- Mechanism (derived, not proven): the entry bundle's `next/cache` import is a different module instance from the RSC environment's cache shim that has the Response Store handler registered; vinext's own handler runs inside the RSC environment.

## 2. Deployed Response Store / tag behaviour (measured)

Setup: Response Store in service-binding mode (own Worker `spike-tmp-plumb-rs` + R2 + SQLite DO `CacheMetadata`), Hyperdrive caching disabled (`cf hyperdrive update <id> --caching-disabled`, `cf hyperdrive create` has no flag; `get` showed `caching.disabled: true`), origin `db.<ref>.supabase.co:5432` as user `postgres` (works from Hyperdrive, per 03 appendix; reads fine here). Truth was an R2 counter object, so the staleness measured is purely the Response Store. Script: `scripts/plumb-cache-test.mjs`. Only one colo seen (`VIE`, same `cf-ray` suffix on all requests); **multi-colo behaviour UNVERIFIED** (I could not originate from another colo). Docs state tag/metadata state is one SQLite DO per key (`vinext/docs/caching.mdx`, "Metadata sharding"), which is the strong-consistency basis, but that is derived.

| Step                                        | Result                                                                                                                                                                            |
| ------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `unstable_cache` read x2                    | second is a hit (`readAt` unchanged)                                                                                                                                              |
| write, no invalidation                      | route, page and ISR page all stale (as expected)                                                                                                                                  |
| write + `updateTag` (Server Action)         | next read of the route, a dynamic page **and an ISR page** is fresh (ISR `x-vinext-cache: MISS` then `HIT`); 12 rapid reads right after: 12/12 fresh                              |
| write + `revalidateTag(tag, { expire: 0 })` | same, all fresh immediately                                                                                                                                                       |
| write + `revalidateTag(tag, "max")`         | route: first read stale, fresh from the second read about 300 ms later (SWR). **ISR page: still stale 17 s later, and 56 s later, and after the data entry itself had refreshed** |

**New: `revalidateTag(tag, "max")` + an ISR/cached page = page stays stale.** In a second run (`isrpoll2.sh` style): the first request after the action got `x-vinext-cache: UPDATING` (stale served, regeneration started); the regeneration re-rendered the page while the tagged data entry was itself still stale, so it embedded the old value, and subsequent requests were `HIT` with the old value (age 4 to 56 s). The data entry only refreshed on the next direct read. Net effect: stale until the page's own `revalidate` (3600 s here). Mitigations: use `updateTag` (actions) or `revalidateTag(tag, { expire: 0 })` for anything feeding a response-cached page (homepage feed), reserve `"max"` for data that is only read through `unstable_cache` in dynamic pages. Consistent with the Response Store README semantics for `invalidate` ("reads keep serving them through their stale-while-revalidate window ... and regenerate them like any stale entry", `vinext/packages/workers-response-store/README.md`); the chained-staleness is my measurement, not documented.

**`cf-cache-status` / headers.** No `cf-cache-status` appears on any app response (the app Worker has `cache: { enabled: false }` by design; the Response Store entrypoint is the cached one and is reached via service binding, `packages/cloudflare/src/cache/config.ts`). The observable header is `x-vinext-cache` (`BYPASS` dynamic, `MISS`, `HIT`, `UPDATING`) plus `age` on hits. `x-vinext-cache` is set by vinext source, not documented in `docs/` (derived from observed values). A standalone Worker with Workers Cache enabled does emit `cf-cache-status` (see 5).

Staleness window summary: with Hyperdrive caching off, no window was observed for `updateTag`/hard `revalidateTag` (single colo); window = indefinite-until-TTL for `"max"` on ISR pages; window = one request for `"max"` on dynamic reads.

## 4. `NEXT_PUBLIC_*` (measured)

Production build output `.cloudflare/output/v0/workers/default/bundle/_next/static/route-*.js` contained `static_literal:\`mark-9f3a1c\``(value passed on the build command line),`origin_literal:\`https://...\``(from`NEXT_PUBLIC_DEPLOYMENT_ORIGIN`in`.env.local`, loaded by the build), and `dynamic_key:process.env.NEXT_PUBLIC_SPIKE_MARK??null`left as a runtime lookup. Deployed`/spike/nextpublic`: `static_literal`and`origin_literal`correct,`dynamic_key`null,`Object.keys(process.env)`has no`NEXT_PUBLIC_*`. So: always write the literal `process.env.NEXT_PUBLIC_FOO`(no destructuring`const {A} = process.env`, no computed key: those variants not tested, assume not inlined), and the variables must be present in the CI build environment (`.env.local` is gitignored).

## 5. Images (measured + docs)

- `IMAGES` binding, R2 object -> `env.IMAGES.input(obj.body).transform({width:256}).output({format:"image/webp"})`: 200, `x-transform-ms: 11` (512x512 PNG, 29 KB). Works deployed (`app/spike/img/route.ts`).
- vinext `/_next/image`: works for **local public files** (`/spike-test.png` through `ASSETS`), format negotiated from `Accept` (avif 5453 B). `url=https://gradivo.jknm.org/x.png` gives **400 "Invalid image optimization parameters"** (`handleImageOptimization`/`fetchAsset` read only local files, `packages/vinext/src/server/image-optimization.ts`, the `dangerouslyAllowLocalIP` comment says the same). **So next/image's built-in optimizer cannot serve the absolute `gradivo.jknm.org` URLs baked into `content_json`.** Needs a custom `loader` (to an R2-backed route using `IMAGES`) or a separate image Worker.
- Caching: three repeat requests all returned `x-vinext-cache: MISS`, no `cf-cache-status`, no `age`. Source states it outright: "vinext has no image cache on any runtime ... every successful response is transformed" (same file, `IMAGE_RESPONSE_CACHE_STATE`). The Response Store does not cache `/_next/image`.
- A standalone Worker with `cache: { enabled: true }` (`spike-img-worker/`) returning the binding output with `Cache-Control: public, max-age=3600`: `cf-cache-status: MISS`, then `HIT` with `age` 2, 4 and an unchanged `x-rendered-at`. Docs say the same: "Responses from the Images binding are not automatically cached ... We strongly recommend enabling Workers Cache" (`cloudflare-docs/.../images/optimization/binding.mdx`, "Enable caching").
- Cost (docs, `images/pricing.mdx`): binding use is billed as **unique transformations, $0.50 per 1,000, first 5,000/month included on Paid**, each (source, params) pair counted once per calendar month, `format` and `quality` excluded from uniqueness, repeats free, `.info()` free. Workers Cache hits do not re-run the Worker.
- Recommendation (derived): **on-the-fly through a cache-enabled path, not pre-generated variants.** Billing depends on unique (source, size) pairs per month, not on requests, so pre-generating saves no money and costs R2 writes plus a variant-sync problem; on-the-fly with a fixed size whitelist (e.g. 6 widths) bounds the count (900 articles x a few images x 6 widths is cheap even if all hit; 5,000 are free). Serve through a Worker/entrypoint with Workers Cache enabled (own entrypoint like the Response Store's, or the R2 custom-domain/Worker owned by the search-local spike) so repeats are HITs; do not rely on `/_next/image`. Avoid the 20 MB input limit (docs, binding `.input`).
